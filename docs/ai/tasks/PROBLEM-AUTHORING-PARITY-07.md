# 现有题型作者工作流审计与统一增强计划

## 状态

`CONTRACT_FROZEN_IMPLEMENTATION_IN_PROGRESS`

本计划基于 2026-09-05 的真实代码与定向测试，覆盖当前已支持的标准输入输出题、函数题，以及后续选择题需要复用的作者工作流。当前只完成审计、契约设计和自审；数据迁移、API、服务和前端增强尚未实施。

## 已冻结契约（2026-09-05）

- 作者读取返回题目、判题配置、能力与有序子项摘要；普通保存采用增量聚合语义，单次请求上限 8 MiB。64 MiB 测试数据继续通过独立批量导入接口处理，一批只生成一个修订。
- `AuthoringVersion` 从 1 开始。元数据、判题定义、测试用例、资源、选择题内容、揭示策略、发布状态的实际变化成功后递增；读取、提交、权限变化和空保存不递增。终止性删除必须校验期望版本。
- 新聚合写接口上线后成为权威入口；旧写接口仅作兼容适配。第一方前端稳定运行一个完整发布周期且旧写接口连续 14 天无调用后，在下一版本移除旧写接口。
- `CanEditProblem` 只管理题面元数据；`CanManageTestCases` 管理判题配置、启动代码、测试点、资源和选择题答案；发布、取消发布、揭示策略需要 Owner/Root 或同时拥有两项能力；协作者管理和删除仅 Owner/Root。
- 草稿只要求可安全持久化，允许缺少完整判题内容；发布和已发布编辑必须通过完整可判定校验。格式损坏、越界、跨题 ID 和不稳定顺序在任何状态都拒绝。
- 活动测试用例使用零基连续 `Order` 和 `(ProblemId, Order) WHERE IsDeleted = false` 唯一索引。重排在题目锁与事务内先移动到不冲突的正数暂存区，再写回最终连续顺序。
- 答案揭示不可逆。发生揭示前策略可编辑；定时时刻已到或提交后策略已向任何提交者披露答案后，不允许改回未来隐藏状态，冲突返回 `409 answers_already_revealed`。
- InMemory 只作单元验证；最终门禁必须包含 Docker PostgreSQL 迁移、并发冲突、排序、文件生命周期、权限裁剪、三题型生命周期、Worker 回归和前端生产构建。

## 统一目标

所有题型都应满足以下作者体验和发布语义：

- 未发布、已发布、取消发布后均可读取和编辑题目。
- 题型对应的判题内容支持新增、查询、修改、删除和显式排序。
- 未发布时保存草稿；已发布时一次有效保存至多生成一个新判题修订。
- 保存失败不得留下部分草稿、部分文件或新的当前修订。
- 历史提交继续绑定原不可变修订；新提交只绑定保存成功后的当前修订。
- 题面文本统一使用现有 Markdown 编辑和安全渲染链路，支持围栏代码块。
- 作者从服务端获得明确能力标记；页面不向无权限用户展示必然失败的编辑、测试点或删除操作。
- 多标签页或多人协作的旧编辑内容不得静默覆盖新版本，冲突返回 HTTP 409。

### 需要增强的差距

| 优先级 | 差距 | 当前影响 | 目标行为 |
| --- | --- | --- | --- |
| P1 | 没有作者聚合保存接口 | 题目配置与测试点分别保存；一次编辑会产生多个修订或中间线上状态 | 一个作者保存事务同时处理元数据、判题配置和完整有序测试点，已发布时至多生成一个修订 |
| P1 | 测试点没有持久化 `Order` | 顺序隐式依赖 `CreatedAt` 和 ID，不能可靠重排 | 草稿和修订都保存连续顺序，作者可显式移动测试点 |
| P1 | 没有作者版本冲突检测 | 两个标签页或协作者可后写覆盖先写 | `AuthoringVersion` 在锁内比较；过期请求返回 409 和当前版本 |
| P1 | 管理列表与权限能力不一致 | 普通出题人能看到全部草稿和操作入口，但部分操作最终 403；隐藏编译文件使用 `CanEditProblem`，测试点使用 `CanManageTestCases` | 独立作者查询返回 `canEditMetadata`、`canManageJudgeDefinition`、`canDelete`；隐藏编译文件与测试点/选择题答案使用同一判题定义权限 |
| P2 | 隐藏编译文件没有更新/替换 | 修改文件只能先删除再上传；已发布题会生成两个修订并短暂缺文件 | 单个原子替换操作写新文件、切换活动资产并生成一个修订；失败清理新文件并保留旧文件 |
| P2 | 已发布题型切换不能与测试点转换一起提交 | 标准题直接改为函数题时旧测试点不兼容，请求失败；作者必须先取消发布并逐项转换 | 聚合保存允许模式、函数签名和完整测试点集合一起验证、一起切换；失败保留旧线上修订 |
| P2 | 重复提交相同内容的有效子操作仍可能增加修订 | 修订历史噪声和额外存储 | 对规范化判题定义计算等价性；无 judge-affecting 变化不创建修订 |
| P2 | 公共详情同时承担部分作者读取 | 同一 DTO 根据角色裁剪隐藏测试点，不适合未来正确答案等更敏感作者数据 | 保留公共详情兼容接口，新增明确的作者聚合 DTO 和端点 |
| P3 | 发布影响在页面中不够明确 | 作者不知道保存会修改线上版本或需要解决冲突 | 显示草稿/线上状态、当前修订、作者版本、未保存提示和“保存后生成新修订”确认文案 |

## 目标数据模型

| 概念 | 权威所有者 | 生命周期与规则 |
| --- | --- | --- |
| `Problem.AuthoringVersion` | `Problem` | `bigint`，任何作者态成功修改后递增；只用于并发控制，不进入判题修订 |
| `TestCase.Order` | `TestCase` 草稿 | 每题活动测试点中从 0 连续排列；发布时复制到修订 `Order` |
| 编程题判题定义 | `Problem` + 活动测试点 + 活动资产 | 可变草稿；已发布成功保存后由 Publisher 生成不可变修订 |
| 选择题内容与正确答案 | 选择题草稿实体 | 后续按相同作者版本、顺序和发布事务接入 |
| 答案揭示策略 | `Problem` | 可变题目级发布配置，适用于选择题所有历史/当前提交；不属于判题正确性修订 |
| 作者能力 | 服务端投影 | 从用户、所有者和协作者权限派生，不持久化到题目，不信任前端判断 |

迁移设计：

1. `Problems.AuthoringVersion` 回填为 1，设为非空并建立 EF 并发约束；所有作者写操作继续先取得现有 problem advisory lock，再比较期望版本并递增。
2. `TestCases.Order` 先可空加入，按每个 `ProblemId` 的 `CreatedAt, Id` 使用 `row_number()` 回填，再改为非空。
3. 为活动测试点建立 `(ProblemId, Order)` 条件唯一索引；重排在事务内使用安全的临时顺序或聚合替换，避免唯一键交换冲突。
4. 不改变 `JudgeMode` 现有数值，不重写历史 `ProblemJudgeRevisionTestCase.Order`。

## 统一作者 API

新增而不立即移除现有接口：

- `GET /api/problems/admin`：返回当前用户可管理或可查看的题目，以及能力标记；管理页面不再从公共题库接口猜权限。
- `GET /api/problems/{id}/authoring`：返回完整作者聚合、`authoringVersion`、当前修订号、发布状态和能力。
- `PUT /api/problems/{id}/authoring`：请求携带 `expectedAuthoringVersion` 与完整题目定义；服务端按题型判别 payload，一次事务保存。
- `PUT /api/problems/{id}/judge-assets/{assetId}`：原子替换隐藏编译文件，请求同时携带期望作者版本。

聚合响应返回：

- 新 `authoringVersion`。
- 是否创建修订、当前修订 ID 和修订号。
- 当前发布状态。
- 规范化后的测试点/小题顺序。
- 能力标记。

现有 `PUT /api/problems/{id}` 和测试点增删改/导入接口先保留，内部适配到同一个 `ProblemAuthoringService`。兼容接口在 advisory lock 内读取当前作者版本并执行单项变更，但第一方前端切换到聚合接口后再评估废弃；不维护第二套发布逻辑。

冲突响应使用 HTTP 409，并返回稳定错误码 `authoring_version_conflict`、当前版本和重新加载提示。校验错误保持 HTTP 400；无权限保持 403；不存在保持 404。

## 状态与保存语义

| 状态 | 允许操作 | 校验与发布效果 |
| --- | --- | --- |
| 新建 | 创建顶层题目 | 始终先创建草稿，获得 ID 和作者版本 |
| 未发布草稿 | 修改题面、模式、函数配置、资源、语言、测试点及资产 | 允许零测试点；每个已保存测试点/资产必须自身有效；不创建修订 |
| 已发布 | 同样的完整 CRUD 与排序 | 对完整候选定义做发布级校验；成功后原子更新草稿，judge-affecting 变化只创建一个新修订 |
| 取消发布 | 保留历史修订并继续完整编辑 | 新提交被拒绝；保存草稿不创建修订；再次发布创建新修订 |
| 删除 | 仅能力允许且无阻塞引用时软删除 | 不删除历史提交、修订或仍被历史修订引用的资产文件 |

presentation-only 字段包括标题、Markdown 题面、标准题输入/输出说明和函数题 starter code；它们更新作者版本但不创建判题修订。judge-affecting 字段包括模式、允许语言、函数签名、时间、内存、测试点、测试点顺序与活动隐藏编译文件集合。

## 服务端事务顺序

1. 验证身份并取得 problem advisory lock。
2. 加载 `Problem`、活动测试点、活动资产和权限；比较 `expectedAuthoringVersion`。
3. 根据标准输入输出/函数/选择题分支规范化完整请求。
4. 草稿状态执行草稿校验；已发布或本次发布执行完整发布校验。
5. 计算 judge-affecting 定义指纹，识别是否真正需要新修订。
6. 在一个数据库事务中更新草稿、顺序和作者版本；需要时调用唯一 `ProblemJudgeRevisionPublisher`。
7. 提交后再返回规范化作者 DTO；任何失败清空跟踪并保持旧当前修订。

隐藏编译文件替换额外采用“先写新物理文件、事务保存新资产并软删除旧资产、失败删除新文件”的补偿流程。旧物理文件继续由历史修订引用，不能立即删除。

## 前端增强

- 管理列表改用作者接口，根据能力显示查看、编辑题面、管理判题定义和删除操作。
- 统一作者页面外壳：基本信息、判题配置、测试数据、隐藏编译文件、发布五个区域；选择题后续复用基本信息和发布区域。
- 标准题测试点和函数题 JSON 测试点支持本地新增、编辑、删除、拖动/按钮排序，点击一次“保存全部”提交聚合。
- 已发布页面显示“本次保存将更新线上判题修订”；纯题面变更显示“不重新判题，仅更新展示”。
- 发生 409 时保留本地未提交内容，展示服务端已更新提示，并提供重新加载；首版不实现自动合并。
- Markdown 继续复用现有编辑预览；不新增另一套富文本格式。测试输入输出和函数 JSON 保持代码/预格式文本展示。
- 隐藏编译文件提供“替换”操作；上传前显示语言、文件名、大小，替换成功后只生成一个修订。

## 与选择题计划的共用边界

- `ProblemKind` 决定作者聚合中的 `programmingDefinition` 或 `choiceDefinition`，`JudgeMode` 只属于编程题。
- 三种题型共用 `AuthoringVersion`、能力模型、状态机、聚合事务、冲突响应和发布结果。
- 标准/函数测试点的 `Order` 与选择题小题/选项 `Order` 使用相同的连续排序规则。
- 选择题正确答案和解析只出现在作者 DTO；公共详情按揭示策略投影。
- 选择题内容变更与编程测试点变更一样生成不可变修订；仅答案揭示策略变化不生成判题修订。

## 分阶段实施

1. **契约登记**：确认聚合 DTO、能力字段、409 错误和兼容接口寿命；登记 PublicApiLedger。
2. **模型与迁移**：加入 `AuthoringVersion`、`TestCase.Order`、条件唯一索引和回填 SQL；验证 PostgreSQL 升级/降级。
3. **统一应用服务**：实现规范化、权限、版本比较、差异分类和单事务保存；Publisher 仍是唯一修订创建者。
4. **现有 API 适配**：加入作者查询/聚合保存；旧题目、测试点、导入接口转调统一服务并保持现有响应兼容。
5. **资产替换**：加入原子文件替换、补偿清理、历史引用保留和权限统一。
6. **现有前端迁移**：管理列表使用能力；标准/函数题使用统一作者页和一次保存；增加排序、冲突和修订提示。
7. **选择题接入**：在已经验证的作者骨架上增加选择题草稿、修订、答题与揭示策略，不复制状态机。
8. **发布验证**：迁移演练、后端定向/完整测试、前端构建、三题型作者 E2E、三语言判题回归。

## 验证矩阵

- 状态：未发布、已发布、取消发布、重新发布下的读取和完整 CRUD。
- 标准题：输入输出、样例/隐藏、分值、顺序、批量替换、Markdown 代码块。
- 函数题：签名、参数/返回 JSON、自定义类型、starter code、语言兼容和模式切换。
- 原子性：组合修改只生成一个修订；任一无效元素导致整个请求无变化；无变化保存不生成修订。
- 并发：两个相同作者版本只有一个成功；另一个得到 409；旧请求不能覆盖新题面、测试点或策略。
- 权限：owner、Root、仅题面协作者、判题定义协作者、无关出题人、答题人。
- 资产：替换成功一个修订；数据库失败删除新文件；旧文件仍可被历史修订加载。
- 迁移：现有测试点顺序稳定回填；历史修订与提交不变；升级、回滚和重复迁移检查。
- 回归：代码提交绑定修订、Worker、C11/C++17/C#、四项性能指标、挑战引用与前端生产构建。

## 自审结论

`REVIEW_PASSED_FOR_PLANNING_ONLY`

- 现有两类编程题并非缺少发布后编辑；主要不足是原子聚合、显式顺序、冲突控制、资产替换和权限表达。
- 方案复用 `Problem`、advisory lock、`ProblemJudgeRevisionPublisher`、软删除与历史资产保留，没有建立平行发布系统。
- 已区分展示字段与判题字段，避免仅改 Markdown 题面时制造无意义修订。
- 旧接口保留为兼容适配层，第一方前端先迁移，不要求一次破坏所有调用方。
- 该方案涉及迁移、网络 DTO、并发与修订权威，最终风险等级为 R4；在明确批准本计划前不得开始实现。
