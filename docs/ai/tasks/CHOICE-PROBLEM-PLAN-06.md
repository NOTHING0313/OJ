# 选择题题型实施计划（侦察与自审版）

## 状态

`IMPLEMENTED_AND_POSTGRESQL_GATES_PASSED`

本文件的产品与技术契约已冻结，并已完成数据模型、迁移、作者 API、答题 API、不可变修订、同步判分、赛季基础分接入和第一方前端实现。静态迁移 SQL、受影响测试、构建、前端门禁，以及 PostgreSQL 16 空库升降级、真实并发版本冲突与重排唯一序门禁均已通过。

统一作者生命周期、作者版本、能力模型、聚合保存和现有编程题对齐方案见 `docs/ai/tasks/PROBLEM-AUTHORING-PARITY-07.md`；选择题实现不得另建一套平行编辑状态机。

## 目标与默认语义

- 题库中的一道 `Problem` 可以是编程题或选择题组。
- 一道选择题组包含 1-N 个有序小题，每个小题为单选或多选，并有独立分值。
- 单选必须且只能有一个正确选项；多选至少有一个正确选项。
- 首版按“正确选项集合完全相等”计分：选少、选多、选错均不得该小题分，不做部分得分。
- 未作答按错误处理；整题总分等于所有小题分值之和；满分才视为通过。
- 题组、小题、选项与解析文本均沿用编程题的 Markdown 模式；围栏代码块使用现有安全渲染链路输出为已排版的 `<pre><code>` 代码块。
- 答案揭示策略由出题者二选一：该用户提交后立即查看，或到指定 UTC 时间后对所有用户统一揭示。
- 选择题在 API/Application 内同步判定并持久化，不进入 Redis、`JudgeJobs`、Worker 或 Docker。

## 已核实的现状

- `JudgeMode` 只有标准输入输出和函数式两种值，职责是描述代码沙箱执行方式，不是顶层题型。
- `Problem`、`ProblemJudgeRevision`、创建/更新 DTO 目前把时间、内存、语言和函数签名视为必需的编程题字段。
- 发布由 `ProblemJudgeRevisionPublisher` 生成不可变修订，`Submission.ProblemJudgeRevisionId` 绑定提交时的修订，DbContext 会阻止修订和绑定被修改。
- `Submission` 当前要求 `Language` 与 `SourceCode`，完成后还会驱动挑战进度、赛季得分、个人记录和提交历史。
- 赛季得分允许时间/内存性能奖励；选择题没有可比的运行性能。
- 公共题目详情与题目管理共用主要服务，但隐藏测试点会按权限裁剪。正确选项需要更严格的独立 DTO，不能依赖可空字段避免泄露。
- Challenge 的 `Algorithm` 任务和 `AlgorithmProblemId` 明确绑定编程题；首版不能把选择题悄悄塞入该语义。
- 前端已经统一使用 `MarkdownRenderer`（`react-markdown`、GFM、换行插件和 `rehype-sanitize`），全局样式已覆盖行内代码和围栏代码块；首版无需引入第二套编辑器或渲染器。当前没有 token 级语法高亮依赖，因此“渲染好的代码块”定义为安全、保留格式且有既有代码块样式，不承诺语法着色。

## 推荐架构

### 1. 顶层题型与编程判题模式分离

新增 `ProblemKind`：

- `Programming = 1`
- `ChoiceSet = 2`

保留现有 `JudgeMode`，且仅在 `ProblemKind.Programming` 时有意义。不要添加 `JudgeMode.Choice`，否则会把“是否执行代码”和“如何执行代码”混为一个维度。

编程专属字段改为可空并由应用层与数据库约束联合保证：

- 编程题：`JudgeMode`、`TimeLimitMs`、`MemoryLimitMb` 必填，语言掩码按现有规则。
- 选择题：上述字段、函数签名、starter code 不适用且必须为空。

这是 R4 持久化和 public API 变更。现有行迁移时全部回填为 `Programming`，不改变任何已有题目或提交语义。

`Problem` 保存题目级可变的 `ChoiceAnswerRevealPolicy` 与 `ChoiceAnswerRevealAt`。它们在未发布和已发布编辑页都可修改：定时策略要求 UTC 时间非空，提交后策略要求时间为空，数据库 check constraint 与应用校验保持一致。该策略控制“何时展示答案”，不是“哪个答案正确”，因此不写入判题修订；修改策略不应伪造一个内容未变化的新判题修订。

### 2. 草稿与发布修订

草稿实体：

- `ProblemChoiceQuestion`: `Id`, `ProblemId`, `Order`, `StemMarkdown`, `SelectionMode`, `Score`, `ExplanationMarkdown`, 软删除/时间字段。
- `ProblemChoiceOption`: `Id`, `QuestionId`, `Order`, `ContentMarkdown`, `IsCorrect`。

发布快照实体：

- `ProblemJudgeRevisionChoiceQuestion`: 修订 ID、来源小题 ID、顺序、题干、单/多选模式、分值、解释。
- `ProblemJudgeRevisionChoiceOption`: 修订小题 ID、来源选项 ID、顺序、内容、正确标记。

正确选项、题干、选项内容和解析属于不可变修订；答案揭示策略属于当前 `Problem` 的可变发布配置。历史提交仍从其绑定修订读取当时正确答案，但能否展示由题目的当前揭示策略统一判断。这样管理员在发布后调整统一揭示时间时，旧提交和新提交不会出现不同揭示时刻。

策略变更必须写安全审计，管理端需提示：已经展示过的答案无法从用户认知中“撤回”。一旦定时揭示到期，或提交后策略已经向任何提交者披露答案，服务端拒绝改回未来隐藏状态并返回 `409 answers_already_revealed`。

继续复用 `Problem.CurrentJudgeRevisionId` 和 `ProblemJudgeRevision` 作为唯一发布权威，不另建第二个 current pointer。`ProblemJudgeRevision` 增加 `ProblemKind`，其编程字段按题型可空；DbContext 的不可变检查扩展到两个选择题快照实体。

公共详情必须从当前发布修订读取选择题，而不是读取可编辑草稿，避免用户看到的选项与提交判定修订不一致。管理端通过独立的受权接口读取草稿与正确标记。

### 3. 原子编辑接口

采用整组替换而不是逐小题即时发布：

- `GET /api/problems/{id}/authoring`：复用统一作者端点；只有具备对应能力的题目创建者、协作者、Root 能读取正确答案。
- `PUT /api/problems/{id}/authoring`：复用统一聚合保存并携带 `expectedAuthoringVersion`；提交完整有序小题数组，完整校验后一次事务替换；若题目已发布，内容变化只生成一个新修订。
- 现有 `GET /api/problems/{id}`：增加 `problemKind` 和不含正确标记/解释的 `choiceQuestions`。
- 现有创建/更新题目请求：增加 `problemKind`、`choiceAnswerRevealPolicy`、`choiceAnswerRevealAt`，并把编程专属字段改为按题型可空。

管理端的题组、小题、选项和解析编辑框复用现有 `MarkdownEditor`；公开题面、作答页与答案解析复用 `MarkdownRenderer`。题干或选项中的围栏代码块（例如 ` ```cpp `）不得转换成 HTML 后保存，数据库只保存原始 Markdown，所有展示点都经过同一 sanitize 管线。

整组接口避免新增/删除一半时生成无效线上修订，也让顺序、总分与聚合大小在一次校验中确定。服务器重新分配连续 `Order`，不信任客户端排序冲突；作者版本不匹配返回 HTTP 409，不能静默覆盖其他标签页或协作者的新修改。

“增删改查”在作者端必须覆盖题组内的小题、选项、正确答案和解析，但 HTTP 写入仍使用一次聚合 `PUT`，不为每个子项增加独立发布端点：

| 编辑状态 | 查询 | 新增/修改/删除/排序 | 保存结果 |
| --- | --- | --- | --- |
| 未发布 | 返回完整草稿、正确答案和揭示策略 | 全部可用；允许暂存尚不满足发布条件的中间稿 | 只更新草稿，不创建发布修订 |
| 已发布 | 同一编辑入口返回完整当前草稿、正确答案和揭示策略 | 全部可用，不锁定已发布内容 | 题目内容/正确答案变化时，完整校验并原子创建一个新修订；失败则线上旧修订和草稿均不发生部分变化 |
| 已取消发布 | 作者仍可完整查询和编辑 | 全部可用 | 更新草稿；再次发布时创建新修订 |

草稿保存只执行资源上限、ID 归属、顺序和基础结构校验，允许暂时没有小题、选项或正确答案；发布或已发布状态下保存执行完整可判定校验。作者界面应在本地编辑完整数组后一次保存，因此删除正确选项、调整单/多选模式等组合修改不会产生中间无效线上版本。

答案揭示策略的修改在三种状态下均可用。它与题组内容可由同一编辑页面提交，但服务端分别判定变更：仅策略变化就原子更新 `Problem` 和审计记录，不创建判题修订；题组内容或正确答案变化才创建新修订。顶层题目删除继续沿用现有软删除与引用检查，不新增物理删除捷径。

### 4. 提交与同步判定

保留一个提交历史聚合，避免挑战、赛季、个人资料和外键全部分叉：

- `Submission` 增加 `SubmissionKind`（`Code` / `Choice`）。
- `Language`、`SourceCode` 对选择题可空；代码提交仍由校验和数据库约束保证非空。
- 新增 `SubmissionChoiceQuestionResult`：提交、修订小题、是否正确、获得分数。
- 新增 `SubmissionChoiceSelection`：小题结果、修订选项；用规范化关联而非 JSON 保存选中项。
- `POST /api/submissions` 继续只接收代码，保持现有调用行为。
- 新增 `POST /api/choice-submissions`，请求包含 `problemId`, 可选 `challengeTaskId`, `problemJudgeRevisionId` 和每小题的选项 ID 集合。

服务必须锁定题目发布身份并要求请求修订等于当前修订；页面过期返回 409，要求刷新，不能拿旧选项去判新修订。所有问题/选项 ID 必须属于同一修订；重复、未知或跨题 ID 直接拒绝。判定、提交明细、挑战/赛季基础分更新在一个数据库事务中完成，不创建 `JudgeJob`。

提交响应增加判别字段和选择题结果；代码提交的 JSON 形状保持原值。答案披露由服务端根据提交所绑定修订中的正确答案、`Problem` 当前揭示策略和注入的 `TimeProvider` 计算，不持久化 `IsRevealed`，也不需要后台定时任务：

- `AfterSubmission`：该提交事务成功后，提交者查看自己的提交即可获得正确选项 ID 与解析。
- `AtScheduledTime`：同一道题的所有新旧修订和提交使用 `Problem` 上同一个 UTC 绝对时间；时间到达前只返回用户所选、提交时间、聚合得分/状态，不返回正确选项与解析；到达或超过该时刻后再披露。
- 管理权限接口始终可读取答案，但普通公共题面永不包含正确标记。

公开与提交详情 DTO 明确返回 `answerRevealPolicy`、`answerRevealAt`、`answersRevealed`。在未揭示响应中直接省略 `correctOptionIds` 和 `explanationMarkdown`，不用 `null` 与空数组混合表达权限。服务端时间是唯一判据，浏览器时钟只用于倒计时显示。

### 5. 计分、赛季与挑战边界

- `ProblemScoreQuery` 按题型选择测试点分数或选择题小题分数，不能把两者相加。
- 赛季允许选择题获得基础分和首次满分时间；选择题不生成语言、运行时间或内存性能候选，管理端隐藏其 benchmark 与性能奖励配置。
- 把 Worker 内当前“完成后应用赛季分”的调用提炼为可由代码判题和同步选择题判定共同使用的应用服务；不要从选择题服务调用 Worker 类型。
- 个人提交列表以 `SubmissionKind` 区分显示，选择题行不渲染语言/时间/内存。
- 首版明确禁止把 `ChoiceSet` 绑定到 `ChallengeTaskType.Algorithm`，服务端保存时拒绝。若产品要求挑战内选择题，后续单独把 Challenge 的 `AlgorithmProblemId` 泛化为 `ProblemId` 并设计团队答题归属；不要用字段名不符的兼容捷径。

## 建议资源边界

全部按 UTF-8 字节和配置项校验，并在发布修订时再次校验：

| 边界 | 建议初值 |
| --- | ---: |
| 每题组小题数 | 1-50 |
| 每小题选项数 | 2-10 |
| 题干 | 16 KiB |
| 单个选项 | 4 KiB |
| 解析说明 | 16 KiB |
| 单小题分值 | 1-1,000 |
| 整题总分 | 不超过 10,000 |
| 整个选择题定义 | 512 KiB |
| 单次答题请求 | 64 KiB，且选择记录数不得超过修订选项总数 |

这些值已经冻结为首版产品默认值；实现必须按 UTF-8 字节和聚合大小在保存、发布与提交入口重复校验。

## 分阶段执行

1. **契约登记**：登记已确认的精确集合计分、满分通过、Markdown 代码块、两种答案揭示策略、赛季纳入方式和 Challenge 首版排除，以及 API 与迁移影响。
2. **领域与迁移**：加入题型、题目级揭示策略、草稿/快照/答题实体、索引、唯一约束和题型 check constraint；回填现有数据；更新不可变守卫。
3. **作者工作流**：实现发布前、已发布和取消发布后三种状态下的整组读取/CRUD/排序/保存，区分草稿校验与发布校验；内容变化原子创建修订，策略变化独立更新并审计。
4. **答题工作流**：实现新请求/响应、当前修订冲突、集合判定、同步事务提交及提交详情/列表投影。
5. **得分与现有功能接入**：总分查询、赛季基础分、个人记录、管理筛选；选择题跳过性能排行；阻止错误的 Challenge 绑定。
6. **前端**：题型选择、揭示策略/时间控件、复用 Markdown 编辑预览、选择题组排序、单/多选作答、定时揭示倒计时、结果与历史展示；编程题编辑器和 Monaco 仅在编程题加载。
7. **迁移与发布验证**：PostgreSQL 升降级演练、老数据回归、三语言判题回归、选择题端到端与构建门禁。

## 验证矩阵

- 判定单测：单选正确/错误/未答/多选，多选集合顺序无关、少选/多选/错选/重复 ID、跨修订 ID。
- 边界单测：0/1/50/51 小题，1/2/10/11 选项，字节边界、多字节文本、分值和聚合溢出。
- 作者工作流测试：未发布草稿允许中间不完整状态；三种状态均可查询、新增、修改、删除和排序；已发布内容变化只生成一个新修订；仅策略变化不生成修订；整组保存失败无部分写入；旧修订不变。
- 发布测试：无小题、无正确项、单选多正确项、多选少于两个正确项、发布校验失败保持原线上修订、取消发布后可继续编辑和重新发布。
- Markdown 测试：题干/选项/解析的围栏代码块、行内代码、GFM 表格与恶意 HTML；编辑预览和公开展示使用相同 sanitize 结果。
- 揭示测试：提交后策略即时可见；定时策略在临界点前一 tick 隐藏、临界点及之后可见；两个用户及不同修订的历史提交在同一时刻统一切换；发布后修改策略立即作用于后续读取；重启后无需任务补偿。
- 保密测试：匿名/普通用户的题目和未到期提交 JSON 中不存在 `IsCorrect`、`correctOptionIds` 与未授权解析；管理端权限正确。
- 并发测试：答题提交与题目重新发布竞争时，要么绑定完整旧/当前策略，要么返回 409，不得混合选项。
- 持久化测试：现有题目/提交回填为编程类型；题型 check constraint；选择题提交没有 `JudgeJob`；级联/Restrict 行为符合历史保留要求。
- 集成测试：多小题（含单选与多选）发布、作答、计分、重试、列表/详情；赛季只计算基础分；Challenge 错误绑定被拒绝。
- 回归：现有不可变修订、代码提交、Worker 租约、C11/C++17/C#、四项时间/内存指标、前端生产构建全部通过。

## 自审结论

`IMPLEMENTATION_REVIEW_PASSED_WITH_POSTGRESQL_ACCEPTANCE_BLOCKER`

- 架构边界通过：选择题不执行用户代码，且不进入 Worker；发布仍只有一个不可变权威。
- 数据一致性通过：正确答案、用户选择、修订选项均规范化存储；没有把复杂结构塞入一个可变 JSON 字段。
- 展示复用通过：Markdown 原文进入既有编辑器/安全渲染链路，围栏代码块不需要 Monaco 或新的内容格式；语法着色明确不在首版承诺内。
- 揭示策略通过：正确答案绑定不可变修订，揭示时间由题目级当前策略统一控制并以服务端时间即时计算；已发布后可编辑，且不引入定时任务、可漂移状态或客户端授权判断。
- 兼容性有明确成本：`Problem` 编程字段与提交 DTO 的可空性属于 public API 变化，必须同批更新第一方前端并记录；实现前需用户确认。
- 已拒绝三个高风险捷径：新增 `JudgeMode.Choice`、另建完全平行的提交历史、用 `Language=0`/空源码伪装选择题。
- 答案揭示策略、资源边界和 Challenge 首版排除均已冻结；选择题不得强塞进现有团队算法任务语义。
